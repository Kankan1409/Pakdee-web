# แผนแยกฐานข้อมูลต่อบัญชี (Supabase project ต่อลูกค้า)

> เอกสารศึกษาก่อนลงมือ (ยังไม่ได้แก้โค้ดตามแผนนี้) — เขียนเมื่อ 2026-11-19
> ทางเลือก: **เราสร้าง project ให้ลูกค้าเอง** โดยใช้บัญชี Supabase หลายบัญชีที่เรามี

## 1. ภาพรวม

```
ฐานข้อมูลกลาง (Registry) — project ของเรา 1 ตัว เก็บข้อมูลน้อยมาก
  ├─ accounts            บัญชีลูกค้า (ล็อกอิน, รหัสผ่านที่เข้ารหัสแล้ว)
  └─ tenant_databases    บัญชีนี้ใช้ฐานข้อมูลไหน (URL, anon key, service key*, สถานะ)
                         * เก็บเข้ารหัส อ่านได้เฉพาะฝั่งเซิร์ฟเวอร์

ฐานข้อมูลลูกค้า A  (project ใน Supabase บัญชีที่ 1)  → ห้อง ผู้เช่า บิล สลิป ... ของ A
ฐานข้อมูลลูกค้า B  (project ใน Supabase บัญชีที่ 1)  → ของ B
ฐานข้อมูลลูกค้า C  (project ใน Supabase บัญชีที่ 2)  → ของ C
...
```

- ลูกค้าแต่ละรายได้พื้นที่ของตัวเอง (แผนฟรี project ละ 500 MB ฐานข้อมูล + 1 GB ไฟล์)
- ข้อมูลแยกขาดจริง: ลูกค้า A ไม่มี key ของฐาน B เลย
- ตารางในฐานลูกค้า = ตารางชุดเดิมที่ใช้อยู่ตอนนี้ (ดูผังฐานข้อมูล) ไม่ต้องออกแบบใหม่

## 2. ต้องรู้ก่อนตัดสินใจ

| เรื่อง | รายละเอียด |
|---|---|
| **เงื่อนไขการใช้งานของ Supabase** | แผนฟรีจำกัด 2 project ที่ใช้งานอยู่ต่อบัญชี การเปิดหลายบัญชีเพื่อให้ได้ project ฟรีเพิ่ม **อาจขัดเงื่อนไขการใช้งาน (Terms / Fair use)** ถ้าถูกตรวจพบ project อาจถูกระงับพร้อมกันทุกตัว — อ่าน supabase.com/terms ก่อน หรือใช้บัญชีที่เป็นของลูกค้าแต่ละรายจริง ๆ (ลูกค้าเป็นเจ้าของบัญชี เราได้สิทธิ์ดูแล) |
| **project ฟรีถูกหยุดชั่วคราว** | ไม่มีการใช้งาน 7 วัน Supabase หยุด project ไว้ (ต้องกดเปิดใหม่ใน Dashboard) — หอที่ไม่มีคนเปิดเว็บ แต่ยังมี LINE เข้ามา จะใช้งานไม่ได้ช่วงนั้น |
| **ไม่มี backup อัตโนมัติในแผนฟรี** | ต้องทำ backup เอง (สคริปต์ `pg_dump` ตามรอบ) ทุก project |
| **ดูแลหลายที่** | แก้ตาราง 1 ครั้ง = ต้องรัน SQL กับทุกฐาน → ต้องมีระบบ migration อัตโนมัติ (ข้อ 4.5) |
| **ไม่อัตโนมัติ 100%** | สร้าง project ใหม่ต้องทำเองใน Dashboard (หรือ Management API ต่อบัญชี) แล้วใส่ URL/key ในหน้าแอดมิน — ลูกค้าสมัครแล้วต้องรอเราเปิดฐานให้ |

## 3. ลำดับการทำงานเมื่อมีลูกค้าใหม่

1. ลูกค้าสมัครบัญชีในเว็บ → บัญชีอยู่ใน Registry สถานะ "รอเปิดฐานข้อมูล"
2. เรา (แอดมิน) สร้าง project ใหม่ใน Supabase บัญชีที่ยังมีที่ว่าง
3. เปิดหน้าแอดมินในเว็บ → ใส่ URL, anon key, service role key ของ project นั้น → ผูกกับบัญชีลูกค้า
4. ระบบรัน SQL สร้างตารางทั้งหมดในฐานใหม่ให้เอง (migration) แล้วเปลี่ยนสถานะเป็น "พร้อมใช้"
5. ลูกค้าล็อกอิน → เว็บเชื่อมฐานของลูกค้าคนนั้น → ใช้งานได้ตามปกติ
6. ลูกค้าใส่ LINE OA ของตัวเอง → ใช้ Webhook URL เฉพาะบัญชี เช่น `https://<เว็บ>/api/line/webhook/U0005`

## 4. งานที่ต้องทำ

### 4.1 ฐานข้อมูลกลาง (Registry)
- project ใหม่ 1 ตัว เก็บ `accounts` (ย้ายระบบล็อกอินมาไว้ที่นี่ — แก้ปัญหารหัสผ่านข้อความเปล่าไปด้วย ใช้ Supabase Auth ของ Registry)
- `tenant_databases`: `account_id`, `supabase_url`, `anon_key`, `service_key_encrypted`, `schema_version`, `status`
- service role key ของลูกค้าเก็บแบบเข้ารหัส (กุญแจถอดรหัสอยู่ใน `.env` ของเซิร์ฟเวอร์เท่านั้น)

### 4.2 ล็อกอินแล้วเชื่อมฐานของบัญชีนั้น (ฝั่งเว็บ)
- ตอนนี้มีแค่ 4 ไฟล์ที่ใช้ client ฐานข้อมูลตัวเดียว (`src/lib/supabase.ts`): `auth-context.tsx`, `database.service.ts`, `supabase-relational.ts`, `database-inspector-modal.tsx`
- เปลี่ยน `supabase` เป็นตัวที่สลับได้: หลังล็อกอินได้ URL + anon key ของฐานลูกค้าจาก API ฝั่งเซิร์ฟเวอร์ แล้วสร้าง client ใหม่
- ล้างแคชในเครื่อง (localStorage / memoryDb) ทุกครั้งที่เปลี่ยนบัญชี กันข้อมูลฐานเก่าค้าง
- ฐานลูกค้าแต่ละตัวยังควรเปิด RLS แบบง่าย (ให้เฉพาะผู้ใช้ที่ล็อกอินของฐานนั้น) ไม่งั้น anon key ที่อยู่ในเบราว์เซอร์อ่านได้ทั้งฐาน — แต่อย่างน้อยก็อ่านได้แค่ฐานของตัวเอง

### 4.3 ฝั่งเซิร์ฟเวอร์รองรับหลายฐาน (งานใหญ่ที่สุด)
- **ปัญหา:** `DatabaseService` เก็บข้อมูลไว้ในตัวแปรกลางตัวเดียว (`memoryDb`) ฝั่งเซิร์ฟเวอร์ ถ้ามี LINE จากหอ A กับหอ B เข้ามาพร้อมกัน ข้อมูลสองฐานจะปนกันในตัวแปรเดียว
- **แก้:** แยกแคชต่อฐาน (map ตาม `account_id`) และส่ง "ฐานของคำขอนี้" ผ่านทุกฟังก์ชัน (เช่น ใช้ `AsyncLocalStorage` ของ Node)
- ไฟล์ที่ต้องแก้: `src/app/api/**` ทุก route, `src/lib/line/*`, `src/lib/payment-slips-server.ts`, `src/instrumentation.ts`

### 4.4 LINE webhook ต่อบัญชี
- route ใหม่ `/api/line/webhook/[accountId]` → หาฐานจาก Registry → ตรวจลายเซ็นกับ OA ของสาขาในฐานนั้น
- `scripts/dev-with-bot.mjs` ตั้ง Webhook URL ของแต่ละ OA ให้ชี้ไปที่ URL ของบัญชีนั้น
- ตัวแจ้งเตือนอัตโนมัติ (`instrumentation.ts`) วนทุกฐานที่สถานะ "พร้อมใช้"

### 4.5 Migration อัตโนมัติ
- รวม SQL ทั้งหมดใน `docs/*.sql` เป็นไฟล์ลำดับเลข `migrations/001_...sql`, `002_...sql`
- สคริปต์ `npm run migrate` อ่าน `schema_version` ของแต่ละฐานจาก Registry แล้วรันไฟล์ที่ยังขาด
- รันครั้งเดียวตอนเปิดฐานใหม่ และทุกครั้งที่ deploy เวอร์ชันใหม่
- ต้องใช้ connection string ของ Postgres (ไม่ใช่ anon key) → เก็บเข้ารหัสใน Registry เหมือน service key

### 4.6 ย้ายข้อมูลเดิม
- ฐานปัจจุบันมีข้อมูลหลายบัญชีปนกัน → สคริปต์คัดลอกแถวตาม `owner_id` / `property_id` ไปฐานของเจ้าของแต่ละคน
- ทำบน project ทดสอบก่อน, backup ก่อน, ตรวจจำนวนแถวหลังย้าย

### 4.7 หน้าแอดมิน
- รายชื่อบัญชีลูกค้า + สถานะฐาน + พื้นที่ที่ใช้ไป + ปุ่ม "ผูกฐานข้อมูล" / "รัน migration"
- เข้าได้เฉพาะบัญชีแอดมินของเรา

## 6. เทียบกับทางเลือกอื่น

| | ฐานเดียว + RLS | ฐานเดียว + ย้ายรูปไป Storage | **ฐานแยกต่อบัญชี (แผนนี้)** |
|---|---|---|---|
| พื้นที่ | รวมกัน 500 MB (ฟรี) | รวมกัน แต่รูปไม่กินฐานข้อมูล → รองรับได้อีกหลายเท่า | ลูกค้าละ 500 MB |
| ข้อมูลแยกขาด | ฐานข้อมูลบังคับ (RLS) | ไม่เกี่ยว | แยกขาดที่สุด |
| ลูกค้าใหม่ | อัตโนมัติ | อัตโนมัติ | ต้องรอเราเปิดฐาน |
| ดูแลระยะยาว | ที่เดียว | ที่เดียว | ทุกฐาน (migration, backup, project หยุดชั่วคราว) |
| งาน | กลาง | เล็ก | ใหญ่ |

**ข้อแนะนำ:** ทำ "ย้ายรูปไป Storage + ย่อรูป" ก่อนไม่ว่าจะเลือกทางไหน — ฐานแยกต่อบัญชีก็ได้ประโยชน์ (500 MB ต่อหอจะพอนานขึ้นมาก) และถ้าทำก่อน การย้ายข้อมูลไปฐานใหม่ในขั้น 4.6 จะเบาลงด้วย

## 7. ต้องตัดสินใจก่อนเริ่ม

1. เงื่อนไขของ Supabase เรื่องหลายบัญชี — ใช้บัญชีของเรา หรือให้ลูกค้าเป็นเจ้าของบัญชีเอง
2. ใครกดเปิดฐานให้ลูกค้าใหม่ และลูกค้ารอได้นานแค่ไหน
3. ทำ backup ยังไง (สคริปต์ของเรา / อัปเกรดบางฐานเป็นแผนเสียเงิน)
4. หอที่ข้อมูลน้อย จะให้อยู่ฐานรวมก่อนได้ไหม แล้วค่อยย้ายออกเมื่อใหญ่ (ทำได้ ถ้าระบบรองรับทั้งสองแบบ — เพิ่มงานเล็กน้อย)
